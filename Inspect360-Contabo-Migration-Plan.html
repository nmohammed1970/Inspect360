2. What is changing (big picture)

The product stays the same (Node API + React UI + WebSockets + Postgres). What changes is how you host, route, and deploy it — and you configure all of that yourself on Contabo.

Current GoDaddy Windows

Users → IIS (80/443) + SSL → iisnode → Node (~5000) → .env / IIS env vars → Postgres (Windows host) → Files on disk (./storage)

Deploy: build → copy to C:\inetpub\wwwroot\inspect360 → recycle IIS.

New Contabo Ubuntu

Users → Caddy (80/443) + auto SSL → Docker container inspect360:5000 → /opt/inspect360/.env → Postgres via Docker name “postgres” → Docker volume (/app/storage)

Deploy: push main → GitHub Actions builds image → SSH → restart container (~1–2 min).

Single container for the app = API + React SPA + WebSocket in one Inspect360 container. Postgres and Caddy stay as separate shared services on the server (infra rule). You do not put the database inside your app image.

What stays the same

  • Same codebase: Express + Vite/React monolith.
  • Same DB: PostgreSQL + Drizzle.
  • Same integrations: Stripe, Resend, OpenAI, Maps, Fixflo.
  • Same domain goal: portal.inspect360.ai.

What you must change

  • No more IIS / iisnode / web.config for production.
  • Only Caddy is public (80/443). App has no public port mapping.
  • App DB host = postgres (Docker service name), not localhost.
  • Your personal GUI (DBeaver) still uses SSH tunnel → localhost:5432.
  • Secrets only in server env / .env on Contabo — never in git.

6. Phase 1 — Code / repo changes

Work in the Inspect360 Git repo so the app becomes a Docker image with auto-deploy.

1.1 Add multi-stage Dockerfile (single app process) You Repo
  • Base: node:20-bookworm-slim
  • Install Linux libs for Chromium (PDF), sharp, ffmpeg
  • npm ci → npm run build → node dist/index.js
  • PORT=5000, uploads at /app/storage
WhyDocker needs a build recipe. Missing Chromium deps = PDF breaks on Linux. No storage path = uploads vanish on restart.
WhereNew Dockerfile in the repo. Built by GitHub Actions; runs on Contabo.
vs currentReplaces IIS/iisnode + web.config packaging for Windows.
1.2 Add compose fragment (no public ports) You Repo Used on Contabo
  • No ports: published to the internet
  • Join existing external Docker network (name from Phase 0)
  • Named volume for /app/storage
  • Env from /opt/inspect360/.env
services:
  inspect360:
    image: ghcr.io/ORG/inspect360:latest
    container_name: inspect360
    restart: unless-stopped
    env_file: /opt/inspect360/.env
    volumes:
      - inspect360_storage:/app/storage
    networks:
      - caddy   # use real network name from Phase 0
    # NO ports: mapping

volumes:
  inspect360_storage:

networks:
  caddy:
    external: true
DATABASE_URL=postgresql://USER:PASSWORD@postgres:5432/inspect360
Inside Docker, host must be postgres, not localhost. localhost is only for your DBeaver SSH tunnel.
WhyPublishing ports bypasses Caddy and breaks the security model. Host postgres uses Docker DNS to reach the DB privately.
WhereCompose in repo (or deploy folder on server). Env file only on Contabo disk.
vs currentIIS binds 80/443 on the machine. In Docker, only Caddy is public; app talks to DB by service name.
1.3 Add GitHub Actions + create deploy credentials You Repo Contabo key GitHub secrets

On push to main: build image → push registry → SSH Contabo → pull → recreate container.

You also create:

  • Limited SSH deploy key/user on Contabo
  • GitHub secrets: registry token, SSH_HOST, SSH_USER, SSH_KEY
WhyTarget flow is “live in ~1–2 minutes, no manual copy.” Without CI you still deploy like GoDaddy.
WhereWorkflow YAML in repo; key on Contabo; secrets in GitHub Settings.
vs currentReplaces manual RDP/file-copy + IIS recycle.
1.4 Fix HTTPS cookies + trust proxy You Repo

Today server/auth.ts has secure: false. Behind Caddy HTTPS you must:

  • Enable Express trust proxy
  • Set cookie secure: true in production
WhyWithout this, browsers may drop session cookies over HTTPS — site “works” but users cannot stay logged in.
WhereApplication source (server/auth.ts, server/index.ts). Not an OS setting.
vs currentCode still has insecure cookie defaults; fix as part of proper HTTPS behind Caddy.
1.5 Add Caddyfile site block (you edit carefully) You Contabo 
portal.inspect360.ai {
    reverse_proxy inspect360:5000
}
  1. Backup the current Caddyfile
  2. Add only this site block
  3. Run caddy validate --config /path/to/Caddyfile
  4. Reload Caddy
  5. Test /ws after deploy
WhyCaddy is the only public entry and auto-issues Let’s Encrypt certs. Without this block, nothing reaches your container on HTTPS.
WhereContabo Caddy config. Snippet can also live in repo docs for reference.
vs currentReplaces IIS SSL bindings (and any nginx sample). Shared Caddyfile means extra care vs editing a single-app IIS site.
